Runbook: NVIDIA Data Flywheel + RAG Blueprint on OpenShift (nvaie-test)

Goal: prove each blueprint runs and meets the plan wording, with as few GPUs and as little production impact as possible. Run Data Flywheel first (max 3 GPUs), uninstall it completely, then RAG (2 x L40S).

Blueprint Version Goal GPUs
Data Flywheel v0.3.1 (last release; deprecated) + NeMo Microservices 25.8.0 Deploy and validate the NVIDIA Data Flywheel Blueprint, including the iterative evaluation and improvement workflow, and the validation of NeMo Customizer and Evaluator. 3 at peak (Customizer + candidate NIM + judge NIM)
RAG Blueprint v2.6.2 (chart v2.6.0), NVIDIA OpenShift Helm guide Deploy and validate the NVIDIA RAG Blueprint on the cluster, including end-to-end functional validation. 2 x L40S (LLM + embedding)

Barebones install: nothing optional is deployed.

Client approvals required (before the day)

Everything else stays inside nvaie-test. These items affect the whole cluster or grant extra permissions, so each needs explicit client approval. Exact object lists: deploy/reports/*.txt.

# Item For What it adds Why needed If not approved
A1 Volcano v1.15.4 batch scheduler Flywheel 11 CRDs (*.volcano.sh), 4 ClusterRoles + 2 ClusterRoleBindings, runtime Queues default/root. No webhooks. 2 pods in nvaie-test. NeMo Customizer 25.8 runs every fine-tuning job through Volcano Customizer cannot run, so the flywheel plan wording is not met
Safety: webhooks patched to act only on nvaie-test (upstream: every other namespace, fail-closed). Removed by helm uninstall.
A2 NeMo Operator CRDs Flywheel 5 CRDs (*.nvidia.com), 4 aggregate ClusterRoles. Controller permissions scoped to nvaie-test. CRDs are deleted by hand afterwards (1.8). Runs Customizer training jobs Flywheel cannot be installed
A3 NVIDIA NIM Operator 3.0.2 (only if the cluster has none) Both 9 CRDs (*.apps.nvidia.com), 3 ClusterRoles, 2 ClusterRoleBindings; operator pod in nvaie-test Both blueprints create their NIMs through it Neither blueprint can start its models
A4 Elastic ECK operator 3.3.2 (only if the cluster has none) RAG 12 CRDs, ClusterRoles; operator in nvaie-test, managing only nvaie-test, webhook disabled RAG's vector database (Elasticsearch) RAG cannot be installed as designed
A5 anyuid SCC RoleBinding (namespaced) RAG Lets ServiceAccounts default, rag-server, rag-nv-ingest, rag-redis-master, nim-cache-sa run as their image's user (NVIDIA's OpenShift design) rag-nv-ingest needs a fixed group (1000) RAG ingestion likely fails
A6 Image registries besides nvcr.io Both docker.io (mongo, redis, Bitnami Postgres, Volcano, seaweedfs, Elasticsearch, ECK operator), registry.redhat.io (nginx proxy) Components of the blueprints Mirror the images, or the affected component cannot start
A7 Possible SCC exceptions at runtime Flywheel Decided case by case if a pod created by NeMo (training, NIM, evaluation) is rejected for asking for a fixed user Cannot be checked before the run That step fails
A8 GPU use Both Flywheel: up to 3 GPUs (any free type), then RAG: 2 x L40S, one after the other Run the models and fine-tuning —

Also to confirm with the client: whether nvaie-test is Kueue-managed (0.3.4) and the quota/LimitRange (0.3.1).

Conventions

  • Run every command from the folder that contains this file (client/), in bash.
  • $ lines are commands; "Expected" blocks show what you should see (names, IDs and ages will differ).
  • STOP marks a step where you must not continue if the expected result is not met.
  • Steps marked DESTRUCTIVE delete things. They always list first; delete only what the list shows.

0. Before you start

0.1 Tools on your workstation

Tool Version Why
oc same as the cluster (4.22) cluster access
helm >= 3.17 (tested with 3.18.4) the SeaweedFS subchart uses fromToml (added in Helm 3.17)
jq, curl, column, sha256sum any scripts

The pre-flight script (0.3) checks all of these.

0.2 Log in and set variables

The account must be able to create cluster-scoped objects for the flywheel install (CRDs, ClusterRoles, webhooks). This normally means a cluster-admin, or a client admin running those steps.

oc login --server=https://api.<cluster-domain>:6443      # as provided by the client
export NS=nvaie-test
export SC=ocs-storagecluster-ceph-rbd                     # the pre-flight tells you if this is wrong
read -rsp "NGC API key: " NGC_API_KEY; echo; export NGC_API_KEY   # never echo it, never put it in files

0.3 Run the pre-flight script

One command runs every check (tools, permissions, quotas, StorageClass, operators, Kueue, a storage write test, an image pull test, free GPUs). It also creates the two secrets the installs need if they are missing. It takes about 5-10 minutes.

bash deploy/scripts/preflight.sh 2>&1 | tee preflight-$(date +%Y%m%d-%H%M).txt

What it changes, all inside $NS: creates the secrets ngc-registry-default and ngc-api (only if missing), links the pull secret to the default ServiceAccount, and creates then deletes its own test objects (one 1Gi PVC + pod labelled nvaie-test=rwtest, one tiny pod per image labelled pull-check=nvaie). Nothing cluster-scoped.

Every line is PASS, WARN or FAIL. The end shows RESULT: READY or RESULT: NOT READY and a What to do list with the exact action for each WARN/FAIL. Fix the FAIL items, then run it again. STOP while the result is NOT READY. Keep the preflight-*.txt file as evidence.

What the warnings and failures mean:

0.3.1 Quotas and limits. If nvaie-test has a ResourceQuota, it must cover, at the same time:

requests limits GPUs
Flywheel, chart pods (incl. Volcano) ~5.1 CPU / 14 GiB ~29 CPU / 42 GiB 0
Flywheel, runtime pods (2 NIMs, training, eval Jobs) set by NeMo, unknown set by NeMo, unknown 3
RAG (incl. both NIMs) ~6.7 CPU / 47 GiB ~32 CPU / 100 GiB 2

If a quota requires CPU/memory requests and limits on every pod, the flywheel's runtime pods (created by NeMo, not by our charts) need defaults from a LimitRange in nvaie-test. Ask the client to add one.

0.3.2 StorageClass. If the class is not called ocs-storagecluster-ceph-rbd, the script prints the sed command that puts the right name into the values files. Run it, then run the script again. If the namespace is not nvaie-test, also run sed -i "s/nvaie-test/$NS/g" deploy/flywheel/values-*.yaml (it is used for RBAC scoping).

0.3.3 Operators. Tells you which operators to install in 0.4. Two results are a hard STOP (contact us): Volcano already installed by someone else, or NeMo already installed by someone else.

0.3.4 Kueue. If the namespace is Kueue-managed:

  • set kueue.queueName: <localqueue-name> in deploy/flywheel/values-nvaie-common.yaml and deploy/rag/values-nvaie.yaml;
  • ask the client whether unlabelled pods are held back. Pods created at runtime (flywheel NIMs, Customizer training, evaluation Jobs, NIM cache Jobs, Volcano pods) cannot carry the label. If they are held, the client must exempt nvaie-test for the test.

0.3.5 PID limit. Recorded only. NVIDIA's OpenShift overlay already handles low limits.

Storage write test fails. The charts set no fixed UID/GID/fsGroup; OpenShift's restricted-v2 SCC assigns an fsGroup from the namespace range, and that is what makes new volumes writable. If a new volume is not writable by a non-root pod, send the script output to the storage admin. The test runs as a Job, so its pod gets the same SCC the real workloads will get. If the output names an SCC other than restricted-v2 (for example an OpenShift AI SCC), the write usually fails because that SCC assigns no fsGroup. That is a namespace/SCC problem, not a storage problem: STOP and send us the output. If the test Job is held by Kueue, see 0.3.4: the client must exempt the namespace.

Image pull fails. That registry is blocked. Check the cluster's ImageDigestMirrorSet (oc get imagedigestmirrorset -o yaml) with the client, or mirror the image. STOP for any failed image that the blueprint you are about to install uses.

0.4 Approvals and prerequisite operators

Get written client approval for everything in section 5.2 before the day. Then, depending on the "Operators" part of the pre-flight output:

Situation Action
NIM Operator present, version >= 3.0.2 Use it for both blueprints. Nothing to install.
A. NIM Operator absent (approved) Install v3.0.2 once, into nvaie-test, straight from NVIDIA's Helm repo (below). Used by both blueprints; removed in 3.
ECK CRD present Make sure the ECK operator watches nvaie-test (checked in 2.3).
ECK absent (approved) Install ECK 3.3.2 into nvaie-test, scoped to it, straight from Elastic's Helm repo (below).
Volcano CRD present (someone else's Volcano) STOP and ask; do not install a second Volcano.
Volcano absent Approved: install Volcano 1.15.4 in 1.2. Not approved: Customizer cannot run (plan wording not met).

Install NIM Operator 3.0.2 (case A, approved only):

helm install nim-operator https://helm.ngc.nvidia.com/nvidia/charts/k8s-nim-operator-3.0.2.tgz \
  --username '$oauthtoken' --password "$NGC_API_KEY" -n $NS --wait --timeout 10m
oc get pods -n $NS -l app.kubernetes.io/name=k8s-nim-operator

Expected: one nim-operator-k8s-nim-operator-... pod 1/1 Running. Creates 9 CRDs (*.apps.nvidia.com), 3 ClusterRoles and 2 ClusterRoleBindings.

Install ECK 3.3.2 (approved only), managing only this namespace and without its validating webhook. docker.elastic.co is blocked on this cluster, so the operator image comes from Docker Hub (same release):

helm install elastic-operator eck-operator --repo https://helm.elastic.co --version 3.3.2 -n $NS \
  --set managedNamespaces="{$NS}" --set webhook.enabled=false \
  --set image.repository=docker.io/elastic/eck-operator --wait --timeout 10m
oc get pods -n $NS -l control-plane=elastic-operator

Expected: elastic-operator-0 1/1 Running.

bash deploy/scripts/gpu-free.sh

Expected (example):

  -> values-layout-l40s.yaml (Customizer on L40S).

How to choose the flywheel layout:

  • >= 1 H200 free and >= 3 free in total: values-layout-h200.yaml (Customizer on H200).

  • The two NIMs (candidate and judge) are created by NeMo at runtime without a nodeSelector. They take whatever GPU is free (any type). Only the Customizer training pod is pinned by the layout file.

1. Data Flywheel (max 3 GPUs)

1.1 Choose the values files

export FW_PKG=deploy/packages/nvidia-blueprint-data-flywheel-0.3.1-nvaie.1.tgz
export LAYOUT=deploy/flywheel/values-layout-l40s.yaml     # or values-layout-h200.yaml (see 0.5)
FW_VALUES=(-f deploy/flywheel/values-nvaie-common.yaml -f $LAYOUT)

1.2 Install

First Volcano 1.15.4 (approval A1), straight from Volcano's Helm repo. NeMo 25.8 bundles Volcano 1.9.0, which does not support this cluster's Kubernetes 1.35, so the bundled one stays off.

chmod +x deploy/scripts/volcano-postrender.sh
helm install volcano volcano --repo https://volcano-sh.github.io/helm-charts --version 1.15.4 -n $NS \
  -f deploy/volcano/values-volcano.yaml --post-renderer ./deploy/scripts/volcano-postrender.sh --wait --timeout 10m
oc get pods -n $NS -l 'app in (volcano-scheduler,volcano-controller)'
oc get queue

Expected: volcano-controllers-... and volcano-scheduler-... both 1/1 Running; oc get queue lists default (and root) within a minute. STOP if either pod is not Running after 5 minutes (logs: oc logs -n $NS deploy/volcano-scheduler); uninstall it (1.8 step 4) and contact us.

Then the flywheel:

bash deploy/scripts/gpu-free.sh | tail -4
helm upgrade --install flywheel $FW_PKG -n $NS "${FW_VALUES[@]}" --wait --timeout 25m

Expected (after 5-15 minutes):

Release "flywheel" does not exist. Installing it now.
NAME: flywheel
NAMESPACE: nvaie-test
STATUS: deployed
REVISION: 1

If it times out, do not re-run blindly. Go to 5 (Troubleshooting) and oc get pods -n $NS.

1.4 Load the sample data and start one flywheel job

Sample data: deploy/flywheel/data/aiva-1.jsonl holds the 300 records of client_id=aiva-1 taken from the blueprint's own aiva_primary_assistant_dataset.jsonl (v0.3.1), the example used in the blueprint docs (checksum in deploy/flywheel/data/SHA256SUMS).

oc exec -i -n $NS deploy/df-api-deployment -- sh -c 'cat > /legal/source/data/aiva-1.jsonl' \
  < deploy/flywheel/data/aiva-1.jsonl
oc exec -n $NS deploy/df-api-deployment -- \
  uv run python /legal/source/src/scripts/load_test_data.py --file /legal/source/data/aiva-1.jsonl

Expected: log lines ending with the records indexed into Elasticsearch, no traceback.

Open two port-forwards in a second terminal (leave it running):

oc port-forward -n nvaie-test svc/df-api-service 8000:8000 &
oc port-forward -n nvaie-test svc/nemo-gateway 8001:80 &
wait

Start the job (back in the first terminal):

curl -sS -X POST http://localhost:8000/api/jobs -H 'Content-Type: application/json' \
  -d '{"workload_id": "primary_assistant", "client_id": "aiva-1"}' | tee /tmp/fw-job.json | jq .
export JOB=$(jq -r .id /tmp/fw-job.json); echo $JOB

Expected: {"id": "<24-hex id>", "status": "queued", "message": "NIM workflow started"} (or similar).

1.5 Monitor (typically 1-2 hours)

watch -n 60 "curl -s http://localhost:8000/api/jobs/$JOB | jq -c '{status, judge: .llm_judge.deployment_status, nims: [.nims[]? | {model_name, status, deployment_status, evals: [.evaluations[]? | {eval_type, progress, scores}], cust: [.customizations[]? | {progress, customized_model}]}]}'"

What happens, in order:

  1. datasets are created and uploaded to NeMo Data Store;
  2. the judge NIM becomes ready;
  3. the candidate NIM meta/llama-3.2-1b-instruct:1.8.3 is deployed (any free GPU);
  4. base-eval and icl-eval run in NeMo Evaluator (judge scores appear);
  5. at the same time NeMo Customizer runs LoRA training (1 GPU, pinned by the layout). Check it: 
    oc get jobs.batch.volcano.sh,podgroups.scheduling.volcano.sh -n $NS
oc get pods -n $NS -o wide | grep -v -E 'flywheel-|df-|nemo-gateway'
  6. customized-eval runs on the LoRA adapter, then the candidate NIM is shut down;
  7. job status becomes completed.

Peak GPU use is 3 (judge + candidate + training). Check with bash deploy/scripts/gpu-free.sh. If the training pod stays Pending with Insufficient nvidia.com/gpu while the other GPU type has a free GPU, see 4 ("Training pod Pending").

bash deploy/scripts/flywheel-check.sh $JOB $NS | tee /tmp/fw-check.txt

Expected, at the end:

PASS job status is completed
PASS judge deployment is ready
PASS base-eval has judge scores
PASS icl-eval has judge scores

1.8 Uninstall the flywheel completely (DESTRUCTIVE, after evidence is saved)

Order matters: remove runtime objects while the operators still run (they own finalizers), then the release.

  1. Delete the job through the API (also removes its NeMo-side deployments/outputs): 
    curl -sS -X DELETE http://localhost:8000/api/jobs/$JOB | jq .
  2. List NIMs created at runtime by NeMo (the judge stays up while the API runs). Delete only these: 
    oc get nimservice,nimcache -n $NS
oc delete nimservice -n $NS <names shown, e.g. modeldeployment-dfwbp-...>
oc delete nimcache   -n $NS <names shown>
  3. List leftover training/Volcano objects; delete only if any are listed: 
    oc get nemotrainingjobs.nvidia.com,jobs.batch.volcano.sh -n $NS
  4. Stop the port-forwards (Ctrl-C in the second terminal), then remove the release: 
    helm uninstall flywheel -n $NS --wait --timeout 10m
helm uninstall volcano  -n $NS --wait --timeout 10m
    Expected: release "flywheel" uninstalled and release "volcano" uninstalled. The second also removes the Volcano CRDs and ClusterRoles (they are templates of that release), and with them Volcano's default/root Queues.
  5. Volumes left behind (Postgres StatefulSet PVCs, datastore-shared-storage which has a keep policy, NIM cache PVCs, training PVCs). List, check, then delete exactly those names: 
    oc get pvc -n $NS
oc delete pvc -n $NS data-flywheel-customizerdb-0 data-flywheel-postgresql-0 \
  data-flywheel-entity-storedb-0 data-flywheel-evaluatordb-0 datastore-shared-storage
# plus any NIM cache / training PVC from the list above (names start with modeldeployment- / the job id)
  6. Cluster-scoped leftovers: the NeMo Operator CRDs are never removed by Helm. Delete them only if 0.3.3 showed nemotrainingjobs.nvidia.com as NOT FOUND before the install: 
    oc get crd -o name | grep -E 'nemo(entityhandlers|entityvalidators|trainingjobs|trainingworkloads|validationjobs)\.nvidia\.com'
oc delete crd nemoentityhandlers.nvidia.com nemoentityvalidators.nvidia.com nemotrainingjobs.nvidia.com \
  nemotrainingworkloads.nvidia.com nemovalidationjobs.nvidia.com
  7. Flywheel-only secrets (keep ngc-registry-default and ngc-api for RAG): 
    oc delete secret -n $NS --ignore-not-found hf-secret
  8. Verify nothing of the flywheel is left: 
    oc get all,pvc,cm,secret,nimservice,nimcache -n $NS
oc get crd -o name | grep volcano.sh || echo "no volcano CRDs"
oc get clusterrole -o name | grep -E 'flywheel-|volcano|vcjob-' || echo "no flywheel/volcano clusterroles"
bash deploy/scripts/gpu-free.sh | tail -4
    Expected: only the two NGC secrets, the default ServiceAccount objects, and (case A) the NIM Operator / ECK pods remain.

2.4 Ingest a sample text document and ask a question

Second terminal (leave running):

oc port-forward -n nvaie-test svc/ingestor-server 8082:8082 &

wait

First terminal:

mkdir -p /tmp/rag-out && OUT=/tmp/rag-out bash deploy/scripts/rag-test.sh | tee /tmp/rag-out/rag-test.txt

The sample deploy/rag/sample/nvaie-validation-note.txt contains invented facts (a "secret validation phrase"). The test asks for them with the knowledge base, which must answer correctly, and without it, which must not. That contrast proves the answer is grounded in the document. Expected (abridged):

PASS ingestor-server healthy
PASS rag-server healthy
PASS ingestion task FINISHED
PASS document listed in collection
ANSWER: The secret validation phrase is "amber lantern seventeen" ... Dr. Ottilie Varga ...
PASS answer contains the planted phrase "amber lantern seventeen"
ANSWER: I don't have information about ...
PASS control answer does NOT contain the phrase (proves grounding)
RESULT: ALL CHECKS PASSED

2.5 Success check and evidence

Success criteria: a sample text document is ingested; a question returns an answer grounded in it (2.4 all PASS).
